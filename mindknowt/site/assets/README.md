# Site images

Every picture on the landing page is a file in this folder. Nothing on the
page draws a device, a plant, a tag or a stroke of lime in CSS or SVG, so
replacing any of these with a real render or photograph is a file swap with
no code change, as long as the replacement keeps the size and the shape
below.

PNG rather than JPEG everywhere because every one of them needs a transparent
background, and at these sizes none of it is big enough to be worth a format
argument. **Deliver replacements at the exact pixel sizes above**: the page
sizes each one as a percentage of the box it sits in, so a different aspect
ratio shifts the layout around it.

## knowt-tag.png

Generated by `tag-disc.py` in this folder, from the app's
`assets/brand/mindknowt-tag-mark.png`.

```
python3 tag-disc.py          redraw it
python3 tag-disc.py test     redraw it, then measure and check
python3 tag-disc.py check    measure and check the committed file
```

The disc fills the middle **74 percent** of the square and the rest is
transparent. That margin is not spare: the contact shadow is painted into the
file and needs room under the disc. `--disc-in-box` in the stylesheet is the
0.74 that turns a box width into a disc width, so a replacement that fills
more or less of its square moves all eight placements.

2000 is twice the largest the page can ever draw it, so it stays sharp on a
phone.

### The measurements

The real product is a 25mm round paper sticker 0.8mm thick, and the printed
mark's rounded rectangle is 0.35 inch tall on it. The script carries all three
as named constants, and `RECT_RATIO` is the quotient that matters:

| | |
|---|---|
| `DISC_MM` | 25.0, the sticker across |
| `DISC_IN` | 0.984, the same in inches |
| `ICON_RECT_IN` | 0.35, the rectangle's printed height |
| `RECT_RATIO` | 0.35 over 0.984, so **0.356** of the disc's diameter |

The mark is placed by its **rounded rectangle**, not by its ink bounding box.
The signal arcs overhang the rectangle's top right the way they do on the
product, so centering on the ink would push the rectangle down and left of the
middle. One routine, `largest_ink()`, finds that rectangle in the source
artwork and again in the finished file. Using the same routine for both is
what keeps the scaling honest.

`tag-disc.py test` fails if the rectangle is not 0.356 of the disc within
0.005, or if its center sits more than 1 pixel from the disc's.

### The look

It is matte paper, not a glossy button, so the face is flat with a tonal
variation of about two levels in 255, no gradient and no inner shadow. There
is no outline ring. The edge is the thin cut the stack photograph shows: a
hairline of slightly darker white, a full ring faded out by a gradient so it
is strongest along the bottom and gone at the top, with no arc end to see.
Under it is a tight contact shadow, about two pixels down with three of blur
at the size the page draws this, in a slightly warm gray at low opacity. It
should look like a thin sticker lying flat, never like one floating.

The five tags in the kit cluster are this one file, each turned a few degrees
by the stylesheet, which turns the disc, the mark and the shadow together as
one object.

## phone-hero.png and phone-kit.png

Frame, screen and island in one image, transparent outside the rounded body.
**No shadow baked in**: the page adds `filter: drop-shadow`, which follows the
alpha of a rounded body, and a render that brought its own would wear two.

For a real device render, the body should touch all four edges of the file
with no padding, and the screen content should already be in it.

The three small phones in the system row are not these. They are plain
captures from `screens/` in a CSS frame, because at 150 points wide that
frame is four lines of CSS and a second set of files is not worth keeping in
sync.

## knowt-tag.png, and the real sticker

The product is a 25mm round sticker 0.8mm thick: flat matte white, a crisp
thin rim all the way round, and almost no thickness to speak of. The file
carries all three. It used to swell along the bottom, which read as a puck a
few millimeters thick, and it had no rim at all, which is the one feature the
product photographs make unmistakable. 0.8 on 25 is three percent, so the
thickness is a hairline and nothing more.

## The step illustrations

Square, transparent, with the pale lime wash included. The Knowt Tag is not
in them: it is `knowt-tag.png` laid over the top by the stylesheet, so one
file still changes every tag on the page.

Three things are shared deliberately, and a replacement should keep them or
the three tiles stop reading as a set:

- **One stroke weight.** 16 units on the 800 box, which is what all three were
  already drawn at and what a replacement should keep.
- **One wash.** `#DDF495`, an ellipse of 324 by 300, centered on whatever the
  tile's subject is.
- **One clear corner.** The lower right, because the stylesheet lays the tag
  badge there on Stick and on Tap at one size and one position. It used to
  hang off two different edges at two different sizes.

**The phones are upright.** They were tilted, and a tilted phone at this size
reads as a phone lying on its side. Step 01 is untouched: the subject is the
plant pot it has always been.

Step 03's screen carries one Knowt row in its done state, the category's pale
tint with a solid check, which is how a completed Knowt actually looks. It used
to be empty. The name on that row is two bars rather than type, because at the
104 to 130 points the page draws this tile, lettering is smaller than a pixel
and reads as grit.

The lime slashes beside them are gone. They were a comic book motion line,
which is not a language the rest of the page speaks. Step 03 carries three
arcs instead, struck in the tag mark's own idiom at the mark's own weight, in
the gap the signal actually crosses between the tag and the phone. Steps 01 and
02 carry none: nothing is being tapped in either, and a motion cue with
nothing moving is decoration.

## Regenerating these

`illustrations.py` draws the three step files and `tag-disc.py` draws the
disc. Both need Pillow, and `illustrations.py` needs Quicksand as a TTF, which
`fontTools` will make from the woff2 beside it. Neither runs as part of
serving the site, which still has no build step: they are here so the next
change to a drawing is an edit rather than a redraw.

## fonts/Quicksand-variable.woff2

One file, the whole typeface, `wght` axis 300 to 700, latin subset, OFL
licensed. `OFL.txt` beside it is the license.

There used to be three files named 400, 500 and 700, and **they were not
three weights**. The 700 file was this variable font. The other two were
`&text=` subsets whose only letter from the alphabet was a capital A, so
anything set at 400 or 500 drew its A from Quicksand and every other letter
from the next font in the stack. That is why one letter in CLEANING, ADMIN
and PLANT looked like a different typeface: every letter except the A was.

Do not go back to per-weight files. A variable font cannot have a weight
missing and cannot disagree with its own name.

### The capital A, audited again

The A was reported as looking wrong a second time, after the per-weight files
were gone. It was audited against the six usual causes and none of them is
responsible. Recorded here so the same ground is not covered a third time.

The glyph is correct. Our `A` is geometrically identical to the one Google
Fonts serves: the same 644 advance, the same two contours of 27 and 4 points,
the same coordinates to the half unit. The 4 point contour is the crossbar,
wound the same direction as the body, so nothing cancels it. It renders: at
11px the A is 6 by 8 pixels and the crossbar is a solid row of them.

What was ruled out, each by measurement rather than by reading the stylesheet:

- **A fallback font.** `CSS.getPlatformFontsForNode` reports one font for the
  whole label, Quicksand. This is the old bug and it is not back.
- **Synthesis.** Advance widths change with weight and are identical under
  `font-synthesis: none`, so the browser is interpolating the axis rather than
  smearing one master.
- **Weight interpolation.** Same evidence: 300 through 700 each measure
  differently and correctly.
- **text-transform with letter-spacing.** The A has the same shape typed as
  uppercase with no transform, and with letter-spacing removed.
- **font-feature-settings.** Computed `normal`, so nothing is applied.
- **A wrong subset.** Our file covers the same 228 codepoints as the upstream
  latin subset, with nothing missing and nothing extra.

One real difference from upstream was found and fixed: the `prep` table had
been stripped. It is the standard seven byte dropout control program,
`SCANCTRL 511` and `SCANTYPE 4`, which keeps thin strokes from dropping out at
small sizes, and `gasp` asks for grid-fitting at every size while nothing was
there to run. It is restored, which makes every table match upstream.

**It is not what anyone is looking at.** Chromium does not run the bytecode:
rendering at 11px is identical with the table and without it, byte for byte.
It is restored because a stripped hinting program is a regression from
upstream that costs nothing to carry, not because it changed a pixel.

The one candidate that could not be tested here is
`-webkit-font-smoothing: antialiased` on `body`. It is a no-op on Linux, which
is where this was measured, and on macOS it switches text to grayscale
antialiasing and renders it thinner than the designer drew it. That is the
only thing left in this stylesheet that measurably changes how small text
looks, and it can only be judged on a Mac.
